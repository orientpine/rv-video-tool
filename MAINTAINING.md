# Maintaining rv

## How a fix reaches an install
1. Branch, fix, and update tests and docs (README, HOWTO, RELEASES) in the same pull request.
2. Review: every change goes through a pull request with at least one review and a green `test` workflow before it is merged to `main`.
   Merge with `gh pr merge <n> --rebase`: no merge commit, and each commit keeps its author. GitHub records the merging account (its GitHub noreply address) as the committer of rebased commits. `scripts/scan-public.sh --git` allows only exact author/committer lines: the project identity plus the lines of a local file that is never committed (`~/.config/rv-video-tool/scan-allow-identities`, here that account address and GitHub's own noreply address), so the scan stays at exit 0 and a real hit is not hidden behind a scan that is always red. Any other identity, or an allowed address anywhere else in the history, still fails. Both local files live only on the maintainer's machine: a new maintainer copies `scan-patterns` and `scan-allow-identities` from the previous one (never through the repo). Until the allow file exists, `--git` exiting 1 with `identities` findings for those two addresses is expected; create it with one exact `Name <email>` line per allowed identity, as printed by `git log --format='%an <%ae>%n%cn <%ce>'`. Never push to `main` directly.
3. Tag: `vX.Y.Z` (Z for fixes, Y for features). Add a Korean and English note to [RELEASES.md](RELEASES.md) and the GitHub release page.
4. Install from the tag, never from a branch: `bash scripts/install.sh https://github.com/orientpine/rv-video-tool vX.Y.Z ~/.local/share/rv-video-tool`. The old copy stays beside it as `<folder>.bak-<time>`. A `dori heavy` helper that serves rv as a tool bundle gets the same tag with `tools.sh rv vX.Y.Z` run as the helper account; it prints `TOOLS_OK ... RV_TREE <sha256> <files>`, which must match the tag's. Without it, heavy jobs for the new version print `HEAVY_HELPER_NOTOOLS` and run on the local machine.
5. Verify: `bash scripts/verify.sh <install folder>` prints `RV_TREE <sha256> <files>`. Run the same command on the tag's files (`git archive vX.Y.Z | tar -x -C <dir>`); the two lines must match. On one machine `diff -r -x VERSION <install folder> <dir>` must print nothing.

## Tests
- `bash scripts/test.sh` runs every test and ends with `RV_TESTS PASS (n)` or `RV_TESTS FAIL <names>`. `bash scripts/test.sh <name ...>` runs only those.
- CI (`.github/workflows/test.yml`) runs the same script plus the regex part of the leak scan on every pull request.

## Leak scan and export
- `bash scripts/scan-public.sh <dir> [--git]`: gitleaks (when installed) plus private IPs, tokens, e-mail addresses, home paths, chat IDs, forbidden paths, and private patterns from a local file that is never committed (`~/.config/rv-video-tool/scan-patterns`). Any non-zero count exits 1; a missing pattern file exits 2.
- PR bodies, comments and release notes go out only through `bash scripts/gh-safe.sh pr-create|pr-edit|pr-comment|issue-comment|release-notes|release-edit <file> [gh args]`, never `gh pr create --body`, `gh pr comment`, `gh release create --notes-file` or the web editor. GitHub keeps every revision of a body or comment and its API cannot delete one, so a scan after posting is too late. gh-safe scans the file and every other argument (the title too) with `scan-public.sh` first; on a hit it posts nothing and prints only the check name and line numbers, never the matched text, and exits 1. `bash scripts/test.sh gh_safe` runs it with a synthetic pattern and a fake `gh`.
- Before the first push from a checkout, install the pre-push hook: `ln -s ../../scripts/pre-push .git/hooks/pre-push`. It runs the scan on every pushed tree and on the patches and messages of the pushed commits, and refuses the push unless every count is 0. Do not run the scan in a pipe in front of `git push` (`scan | tail && git push` pushes even when the scan fails).
- For a linked worktree, keep the hook in that worktree's Git directory: `hooks="$(git rev-parse --absolute-git-dir)/hooks"; mkdir -p "$hooks"; ln -s "$PWD/scripts/pre-push" "$hooks/pre-push"`. Push with `git -c core.hooksPath="$hooks" push ...` to use it without changing other worktrees' hooks.
- Run `git fetch origin main` before rebasing and pushing. The hook reads the destination remote's branch heads with `git ls-remote <remote-url> 'refs/heads/*'`, using the remote URL supplied by Git to the hook and exact ref names rather than local tracking refs. For both new branches and updates (including `--force-with-lease`), it scans `git log <local-sha> --not <present-remote-head-shas>`. This excludes commits already reachable from any remote branch, including maintenance branches, while retaining every new commit's author, committer, message and patch, including text removed before the tip. Remote heads whose commits are unavailable locally are not excluded, so more history is scanned. The pushed tree is always scanned in full, even when no new history remains. If the remote cannot be read, exact `refs/heads/main` is missing, or its commit has not been fetched locally, the push is refused with a request to `fetch origin main first`. A branch not based on remote main (no merge-base) is also refused.
- `bash scripts/test.sh pre_push` exercises the hook against a temporary bare remote, including a rebased force-push and branch-local leaks. It uses synthetic patterns through the existing `RV_SCAN_PATTERNS` override and clears `RV_SCAN_EXTRA` and `RV_SCAN_ALLOW_IDENTITIES` so local private files are never used.
- `bash scripts/export.sh <checkout> <rev> <dest> <version> --public` builds a one-commit repository from a commit, drops the paths in its `PRIVATE_ONLY` list, and refuses to commit or tag unless the scan prints 0 for the tree and the new history.
